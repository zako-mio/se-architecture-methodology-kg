## §3 原理 · 为什么

在源码缺位时，架构仍可从设计文档被结构化理解。该案例把一组散文式设计文档当作事实来源，先用架构师视角提炼项目定位、核心思想与技术栈，再把「模块是什么、谁依赖谁、数据如何流动」转写为可核查的图结构。关键在于：DAG 不是文档的摘要，而是对文档中隐含依赖关系的一次显式重建——模块清单给出静态结构，依赖边给出耦合方向，拓扑分层给出构建与风险顺序，数据流 DAG 给出运行时行为。作者提出的「服务器只是一种节点角色」「渐进式去中心化」「本地优先加不可变事件」「至少一次投递加幂等」等主张，本质都是架构取舍，逆向过程即把这些取舍还原为可讨论的设计决策。此外，逆向分析不等于替作者背书：它把设计主张与代价并列呈现，使「这算不算好架构」取决于具体场景而非作者自评；显式重建还须标注哪些依赖是强约束、哪些只是当前实现选择，因为后者在演进中可被替换，前者不易。

## §4 机制 · 如何运作

执行采用三路并行、单一聚合的委派结构。第一路以软件架构师视角做全景理解（定位、核心思想、架构、技术栈、威胁模型与评价）；第二路做模块化 DAG 结构化，产出 18 模块清单、约 60 条依赖边（接口依赖、基础设施依赖、事件依赖三类）、L0 至 L6 拓扑分层与构建顺序，以及发送、接收同步、群组控制平面三条数据流 DAG；第三路以需求工程视角做四层需求体系（业务目标、用户故事、功能需求、非功能需求与架构需求）、用户故事、需求缺口与 MVP 成功标准对照。三路之间不设串行依赖，因其输入同为同一批文档、输出面向不同问题，可完全并行；主 Agent 只做口径归一与合成，避免重复阅读整仓，是把上下文成本压到关键的一步。聚合时对三份产出交叉核对：模块清单与数据流涉及的组件是否一致、需求是否覆盖核心思想、拓扑顺序是否与约束自洽，出现口径冲突由主 Agent 终裁。

## §5 工程 · 怎么落地

素材获取不逐页抓取，而是用 GitHub API 拉取整仓文件树后经原始链接批量下载全部 58 个 Markdown，直连优先、代理回退，显著降低时延与请求数。综合文档分三步写入并逐段校验章节完整性；交互式 DAG 图为自研 SVG 数据驱动渲染，节点悬停显示职责、点击高亮局部依赖子图、可切换基础设施边与事件边显示、以 L0 至 L6 底色表达分层，离线可用。交互图把数据与渲染分离，节点与边以结构数据驱动，视图切换只改边集过滤而不重排，因此能在离线单文件中提供可探索的依赖阅读体验。质量门控覆盖 UTF-8 无替换字符、div 开闭平衡与标签完整性；留档按固定五段模板输出（当时情况、制定计划、执行情况、完成情况、反思建议），使后续同类任务可直接比对流程与成本。

## §6 权衡卡

### 代价 · 风险

- 自研 SVG 图适合离线但交互深度有限（无缩放平移），换行图库可增强却引入依赖与构建成本。
- 另一个隐含取舍是自动化程度与人工判断的边界：批量下载与图渲染可自动化，但「哪些依赖重要、哪处设计存疑」仍需人工裁决，工具只降低搬运成本、不替代判断；规模较大时方法成本主要来自阅读与裁决而非抓取，因此文档语言一致、结构规整的项目收益最大。

### 原文要点

- 纯文档逆向有天然边界：文档只表达作者意图，无法验证可编译性、性能与边界行为，DAG 的依赖边也是推断而非实测，需标注置信度。
- 该案例把需求缺口（无障碍、性能量化、数据删除语义等）作为对作者设计的增值评审，但批判性输出与「用户只要客观转述」之间存在张力，宜前置确认语气边界。
- 更根本的取舍是信息完整性对认知负荷：模块越细、边越全，图越忠实也越难读，必须靠分层与折叠控制阅读路径。
