## §3 原理 · 为什么

工具接入的稀缺资源不是磁盘或算力，而是每个 Agent 提示词里被工具定义长期占用的上下文预算。工具 schema 会注入每一个子Agent 的提示词，固定开销随工具数量放大，直接压缩有效工作窗口——这意味着「多接几个工具」的代价是全局的，而非局部的。因此选型不能只看「能力多强」，必须把常驻 token 成本、与既有能力的重叠度、以及是否真增量当作一等公民。核心判断标准从「它能不能做这件事」变成「为这件偶发的事，值不值得在每次调用里都支付固定成本」。这就是够用原则在工具生态里的具体形态：宁可少而精，不要多而全；每多一个常驻工具，都是对所有任务征税。把这项固定成本前置到选型阶段逐项称量，远比在运行中才发现有效窗口被悄然挤占、再回头精简既有能力要便宜，也更不容易引发团队对工具治理的抵触。把工具视为有租金的资产而非一次性安装的功能，选型的心态就会自然从「尽量多」转向「尽量省」。

## §4 机制 · 如何运作

方法分三阶段。第一，实测而非照搬文档：统计每个候选的真实工具数与常驻 token（有的候选实测工具数高于文档声称，有的候选虽有十余个工具但默认只启用两个），因为文档常滞后于代码，厂商口径也可能乐观。第二，构建多维对比：能力矩阵覆盖本地代码关系查询、库文档检索、百科、联网语义搜索、URL 抓取；部署形态区分本地建索引与远程托管；再标注数据外发与认证方式，把安全边界纳入选型。第三，做与内置工具的冲突分析——某个联网抓取工具与内置网页抓取重复、某代码图工具与探索子Agent 互补。据此给出分级方案：最小开销者首选，唯一真增量者追加，重且低频者默认禁用按需开启，已失效者直接剔除。整个对比过程要求每一步都保留数字与出处，使结论可被质疑、可被复核、也可在新版本下重跑，而不是停留在「感觉这个更轻」的模糊判断上。对于相互替代的候选项，对比表还给出「若移除谁、保留谁」的取舍顺序，使结论可直接转成行动。

## §5 工程 · 怎么落地

决策以「累计常驻 token 是否可接受」为硬阈值：基线约三千 token，接入后累计若逼近八千则判为过高。安全维度要求显式标注数据外发边界（哪些候选会把内容发往云端、哪个把图数据留在本地），避免为便利牺牲数据边界。接入策略区分常驻与按需两类：把「需要先建索引、调用频率低」的重能力降级为手动开启，避免为偶发需求支付持续成本；把「体积小、纯增量」的能力列为常驻。最终产出一张可直接执行的接入顺序表与回滚方案，而非一堆孤立评测，使决策可复现、可复核、可随版本更新。接入顺序表还标注了每一项的触发条件与移除方式，便于在需求消失或版本变化时随时回退，也预留观测手段用真实用量反哺下一轮评估。整个过程强调可复现：任何人按同一口径重测，都能得到相近的量级判断，而不必信任某个人的主观描述。

## §6 权衡卡

### 代价 · 风险

- 把重能力降级为按需虽省下常驻成本，却增加了使用时的心智负担与操作步骤，可能在实际任务中因「懒得开启」而失去价值。

### 原文要点

- 对比结论有时效性：工具数、token 估算与限流政策会随版本漂移，star 数也不等于适配度。
- token 估算依赖具体客户端如何注入 schema，与真实占用存在偏差；「唯一真增量」的判断建立在既有内置能力不变的前提上，一旦内置补齐语义搜索，该工具的增量即归零。
- 本案例真正的产出是以稀缺资源为轴做选型的框架，具体数字必须按当时快照解读，不可当作长期结论；选型决策应随版本定期复核，并把「未接入」也视为一种有效决策。
- 因此这类选型报告必须写清版本与日期，并把复核动作制度化，而不是当成一次性结论存档；更要接受「当前最优」随时可能变成「次优」。
- 最后应把「暂不接入」也写成有理由的结论，避免下次讨论时重新从零争论一遍。
