## §3 原理 · 为什么

云架构的核心难题不是缺少选项，而是如何在众多服务与配置间做出可解释、可维护的选择。Google Cloud Well-Architected Framework（原名 Google Cloud Architecture Framework）以支柱表示针对某一非功能关注点的原则与建议，以视角表示面向特定技术或行业的跨支柱视图，为架构师、开发者与运营者提供结构化的设计指引。其官方定位是提供帮助团队设计并运营安全、高效、韧性、高性能、成本有效且可持续的云拓扑的建议，并由 Google 跨职能专家团队校核、随云能力与行业实践更新。框架给出五条跨支柱核心原则：面向变化设计、记录架构、简化设计并优先使用全托管服务、解耦架构、采用无状态架构，把可演化性、可文档化与解耦确立为贯穿所有支柱的立场。这些跨支柱原则并非并列口号，而是相互支撑：面向变化设计需要解耦与无状态作为基础，记录架构为变更影响分析提供依据，全托管服务则把运维负担转为平台责任。

## §4 机制 · 如何运作

框架沿支柱→核心原则→建议的层次组织。六大支柱各有明确的核心原则清单：运营卓越强调用 CloudOps 保障就绪与性能、管理事件与问题、优化资源、自动化变更、持续改进；安全支柱主张默认安全、零信任、左移安全、主动防御、安全使用 AI、满足合规与共享责任；可靠性支柱要求以用户体验定义可靠性、设定务实目标、用冗余与横向扩展构建高可用、用可观测性检测故障、为优雅降级与数据丢失恢复做测试、做实复盘；成本与性能支柱分别围绕价值对齐与持续优化、资源规划与弹性；可持续性支柱关注低碳区域、能耗优化与能效软件。AI/ML 与金融服务视角则跨支柱整合专门建议。Sustainability 于 2026-01 由章节升级为完整支柱。值得一提的是，支柱与视角是正交的两个组织轴：支柱回答关注什么，视角回答为谁、在哪个领域关注，因此同一视角可横跨多个支柱，引用时不应把视角误当作第七个支柱。

## §5 工程 · 怎么落地

落地时可按支柱建立评审清单，并结合 Google Cloud Architecture Center 的参考架构、决策树与 Well-Architected 评审流程使用。工程建议：先定义业务驱动与质量目标，再把框架建议映射到具体场景，避免把使用全托管服务等建议无条件接受；对跨支柱视角（AI/ML、金融）按行业约束裁剪；用架构文档记录选择与理由，并与 ADR、适应度函数联动；把可靠性、成本的持续优化做成常规度量，而非一次性评估。Google Cloud 的能力与命名会随产品发布变化（如 2024-10 移除 System Design 类别、2026-01 将可持续性升为支柱），因此应订阅 What's new 并定期复核所依据版本，防止把当期分类当作长期稳定知识。

## §6 权衡卡

### 代价 · 风险

- 该框架与 AWS 框架高度同构，但同构并不等于可互换：其核心原则明确写入优先使用全托管服务，体现 Google Cloud 的服务导向，会引导架构向 GCP 服务组合收敛，存在厂商绑定风险。

### 原文要点

- 分类法也随产品与市场调整（如移除 System Design 类别、支柱变更），稳定性弱于 ISO 等中立标准；对多云与私有化场景覆盖有限。
- 厂商建议面向推荐做法而非证明正确，无法替代基于质量属性场景的架构权衡分析。
- 因此应以中立标准和场景化评估为主干，把厂商 WAF 作为落地补充，并在引用时统一标注 tier=S3 与厂商立场。
