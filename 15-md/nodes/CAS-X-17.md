## §3 原理 · 为什么

复杂交付的失败多源于在没有证据时过早做技术选择。该方法用两次共识分离两类决策：检查点一只收敛边界（定位、受众、范围、形态），此时不做选型；检查点二在拿到本地与联网证据之后，才收敛技术细节与「为什么选它」。先定边界、后定细节，使每个技术选择都有可比选项与证据支撑，避免拍脑袋式选型带来的返工。同时，这套流程不是人肉规则，而是由双模式协作、拷问协议、复杂度门控、调度者与执行者分离等功能架构托举的——不理解这层隐藏地基，方法论无法复制，只会退化成一张漂亮但跑不动的流程图。方法可迁移的前提，是执行环境具备对应的能力，否则再好的流程也无法落地。换句话说，它把「想清楚再动手」这句朴素经验，拆成了可执行的检查点、角色分工与门控，使方法论不依赖某个人的经验与状态。它把个人经验转成组织能力，使交付质量不随执行者状态波动而剧烈起伏。这套方法的核心不是流程本身，而是把判断建立在证据而不是直觉上。

## §4 机制 · 如何运作

流程为四阶段加迭代与留档。第一阶段做初步分析与计划，用拷问协议收敛边界；协议要求一次只问一个问题、给少量具体选项、能用探索回答的绝不问用户，从而把模糊需求快速压成决策树。第二阶段做精准知识获取，本地与联网深挖，证据落盘且一手优先。第三阶段统合并做第二轮共识，收敛技术细节。第四阶段实现，契约先行、并行实现、集成收口、多轨门控、部署。第五阶段与标杆对照并采纳改进，再门控再部署。全程由复杂度门控按任务规模分配推理预算，主Agent 只做编排与聚合，独立任务并行、有依赖串行接力，子Agent 返回结构化结果以便聚合与交接。每个阶段都有明确的输入、产出与退出条件，任一环节不合格就退回上一步，避免把错误的假设一路带到实现阶段才暴露。门控并非越严越好，其阈值应随任务复杂度自适应，否则会在简单任务上制造无谓阻力。退出条件让每次收敛都有明确的完成标准，减少反复与范围蔓延。

## §5 工程 · 怎么落地

该案例以一个真实的 GitHub 技术知识中枢主页为实证：一次收敛十余个决策、全程零返工，调度九个子Agent（调研、评审、实现、视觉）完成从需求到上线的交付。方法论本身被写成不绑定技术栈的「流程加隐藏地基加可复用模式」三段，并配套质量门控脚本，可直接作为其他母库的编排与交付结构参照。报告双版本（AI 友好 Markdown 与人类可读 HTML）使成果既便于检索又便于阅读，留档与证据同存则保证后续可追溯、可复核、可交接给下一位执行者。这种结构也让过程可审计：任意一次交付都能回答决策何时做出、依据什么证据、由谁收敛，从而支持复盘与经验沉淀。留档与反思环节把每次交付的得失沉淀回体系，使方法论本身也具备迭代能力。可审计性也让新人能从档案里快速理解某个决策的来龙去脉。

## §6 权衡卡

### 代价 · 风险

- 方法论的收益来自用确定性的前期投入换取后期的可控与可演进，代价是流程本身的重量：拷问与两轮共识在需求本就清晰或极小的任务上会变成额外开销，四阶段加门控链对单人快速原型明显过重，管理不当会拖慢节奏。
- 它强依赖 Agent 功能架构的完备（双模式、门控、子Agent 委派、视觉降级），换到能力不足的执行环境会退化甚至无法运行。
- 更现实的态度是按任务风险裁剪流程深度：高风险、多产物的任务走全流程，低风险任务允许走快速通道，而不必一律套用。
- 按风险裁剪流程，是在可控与效率之间取得平衡的现实做法。

### 原文要点

- 不绑定技术栈既是优点也是边界：它只保证过程可复现，不保证产物质量；「零返工」的实证来自单一项目，样本有限，普适性仍需更多场景验证。
- 此外，把决策权交给拷问协议与门控，也可能削弱对特殊任务的灵活判断，需要保留人工否决的通道。
- 对追求速度的一次性任务，可以采用简化版：只保留边界确认与产物门控两步即可。
