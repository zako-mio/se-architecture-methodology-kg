§3原理 · 为什么

逆向一个成品扩展的价值在于还原「为什么这样分层」。该案例的显著主张有三条：其一，把「如何适配不同招聘网站」从核心逻辑中分离为可注册的站点适配器，用域名正则、置信度、探测选择器与容器选择器描述站点差异，运行时评分选择最佳适配器，使新增站点只加数据不改引擎；其二，把「处理页面的能力」与「持有密钥、调用 AI 的能力」拆到不同进程，content 永不接触 API 密钥、background 永不操作 DOM，二者经明确的消息命名空间与统一响应信封通信；其三，隐私优先以脱敏函数在发送前拦截真实简历值，模型只接收字段名与结构。这种「显式外置」也解释了为何一个功能看似简单的扩展会有近万行代码：复杂度并未消失，而是被搬到边界与适配层集中管理；反过来说，若把适配逻辑写进引擎、把密钥放进页面脚本、把真值直接发给模型，短期代码更少，长期每一次站点改版、每一次隐私审计都会放大成本。

§4机制 · 如何运作

四模块职责清晰：popup 是用户操作入口，经 tabs 通道下发页面级指令；content 是注入页面的引擎，承担表单扫描、字段标签提取、语义桶匹配、候选评分、控件填写与绿橙标记；background 是 Service Worker 中枢，持有配置、代理 AI 调用、巡检更新并经 runtime 通道路由十余种消息；options 管理结构化简历、AI 接口配置与导入导出。核心机制包括适配器模式（站点探测与统一注入扫描管线）、评分链模式（硬过滤后经文本分、语义桶加分、重复项序号匹配加权，达阈值才自动填写）、双通道协议（页面操作走 tabs、服务调用走 runtime，消息以命名空间隔离）、以及为兼容 React/Vue 受控组件的原生 setter 加事件派发写入法。值得注意的取舍是「谁来做决策」：站点探测在页面进程做，AI 调用与密钥在后台进程做，二者以消息解耦，使替换 AI 后端或新增站点互不影响；标记系统用颜色把「已自动填写」与「待人工确认」分开，本质上把模型置信度外化为可见信号，而非静默替用户决定。

§5工程 · 怎么落地

工程上以零 package、零 node_modules、零打包器实现，Load unpacked 直接加载，把部署复杂度压到最低，代价是全部逻辑靠手写原生 JS 承载，核心文件达数千行。隐私以「发送前脱敏、提示词只含字段结构」落实，避免简历真值出域；更新检查用定时闹钟加发行接口并配徽标提示；面板状态以会话存储加 LRU 控制上限；填写入口用运行标识双重检查防重入；面板持久化加防抖。文档化方面配套模块依赖与数据流图、核心流程时序图与适配器机制图，把逆向结论沉淀为可复用资料。整个扩展的可审计性正来自「无构建」：源码即产物，任何人拿到压缩包即可逐行检查其网络请求与数据处理，这对处理敏感简历的工具有现实意义；代价是没有依赖管理，跨文件复用只能靠约定与全局常量，演进到更大规模时需要重构而非简单加包。

§6权衡卡

代价 · 风险

零构建选型以可维护性换来了交付简单与审计透明：省去工具链却失去类型检查与模块打包，数千行单文件与全局常量使大型化后风险陡增；适配器驱动降低新增站点成本，但适配器质量参差会直接决定填写准确率，且站点改版时适配器需持续维护。

AI 调用无缓存，每次填写独立请求，准确率提升以用户 API 成本为代价。

更深的张力在自动化程度：自动填写越激进，用户越省事，误填风险也越大，本案例用阈值加颜色标记把不确定交还用户，是保守但有据的选择；另一个被低估的成本是站点维护，适配器增长后每个都是一条需持续回归的测试路径，缺少自动化站点测试时维护负担会随覆盖站点数上升。

反例 · 误区

双通道协议边界清晰，却需要人工维护十余种消息与两端契约，缺少自动化交叉校验时易出现漏接与静默失败。
