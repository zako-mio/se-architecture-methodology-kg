§2局部关系图

§3原理 · 为什么

该案例把知识图谱的依赖证据模型迁移到第三方插件分析。命题是：一个包「依赖什么」不能只看清单，而须由三层证据交叉确认——编译依赖来自清单声明，运行时依赖来自上下文服务注入与调用，组合依赖来自装配文件中的挂载位置；三者结合才能区分「声明了但没用」「没声明却在用」「在哪被装配」三种情况。在此之上做需求溯源，把每项功能映射到它解决的痛点，再把设计问题分为高、中、低并按证据列出。方法要求所有结论附源码行号，使判断可被复核而非停留在印象；同时要求把第三方插件消费的宿主能力对齐到知识库中真实存在的节点标识，而不是泛化的包名，从而让新分析与既有图谱无缝互查。三硬依据的价值在于把「依赖」从单一来源的断言变成可交叉验证的证据链：声明、注入、装配分别对应发布、运行与部署三个视角，任一口径单独使用都可能误导。因此证据链须逐条落到源码行号，使不同视角之间的冲突能被准确定位而非被平均掉。

§4机制 · 如何运作

执行先克隆源码并记录提交哈希，主 Agent 只读装配文件与提取上游节点，把大体量代码拆给并行的探索子 Agent：服务端半区负责服务注入证据、远程调用面、功能机制与安全观察，浏览器半区负责插槽注入清单、字典、面板结构与设计问题观察。两路均以行号固证，主 Agent 裁决后组装结构化数据（若干核心节点、宿主依赖桩节点、边、功能、需求与设计问题），再生成单页交互图。两路并行不仅提高吞吐，也让证据来自不同视角：服务端半区聚焦运行时注入与远程调用面，浏览器半区聚焦插槽注入与界面结构，二者在「同一插件如何横跨两个半边」上互补；主 Agent 的裁决职责是把两半区口径统一，并对设计问题按高危、中危、低危排序，避免以风格偏好冒充缺陷。分析结论包括：该插件是传输面注册型宿主扩展，双半边架构经同源接口闭合，四大功能与六类痛点一一对应，九项设计问题含鉴权弱与脚本补丁自认非硬边界等。

§5工程 · 怎么落地

工程要点有三：其一，宿主依赖桩必须带组别与拓扑层标注，并尽量对齐知识库真实节点标识，使第三方分析可回查宿主结构；其二，可视化用单页交互图，本地内置依赖、点击弹详情卡，门控覆盖编码无替换字符、标签闭合、内嵌数据合法、本地依赖路径存在、无外部内容分发网络、画布实际着色与交互可用；其三，渲染验证不迷信视觉模型：对深底小字，视觉转写多次互相矛盾，应改用像素计数确认非空白加实例接口逐节点取真值，视觉模型只用于布局与乱码级粗检。方法论按需裁剪：版本级联工作流只复用其源码获取规范与三依据判定，差异分析部分不适用。对齐宿主节点标识有两个好处：桩节点带有组别与拓扑层后读者能直接理解其在宿主中的位置，且分析结果可与既有图谱数据互查，形成「主图加增量分析」的组合，而不必重建平行体系。

§6权衡卡

收益 · 正确姿势

设计问题裁决触及第三方上游，价值高但需谨慎：应以证据与影响排序，避免把风格偏好当缺陷。

代价 · 风险

以三层证据加行号固证提高了结论可信度，代价是分析成本高、需要读装配与源码并维持证据链条，轻量巡检并不划算。

渲染验证的方法教训是取舍的典型——视觉模型适合粗检而不适合精确标签核验，过度信任会把幻觉当成结论，改用确定性接口取真值虽更可靠却要求被测系统暴露可查询状态；此外以行号固证会使报告偏长，用于速览时需另行抽取结论层。

原文要点
  • 把宿主能力对齐到既有图谱节点增强了互查性，却引入对上游图谱版本的依赖：图谱演进后桩节点映射可能失效，需回归维护，因此第三方分析应与图谱版本绑定并标注基线。
  • 并行拆分服务端与浏览器半区提高了吞吐，但两半区口径需主 Agent 统一裁决，否则会出现同一功能描述不一致。
