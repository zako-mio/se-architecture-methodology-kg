# F · 概念与需求（Concept & Requirements）证据包摘要

> 阶段2 F 域产出｜访问 2026-09-10｜配套 `F-requirements.json`
> 覆盖：SWEBOK V4 KA1 · 软件危机与本质复杂度 · ISO/IEC/IEEE 29148:2018 · 干系人识别 · 质量属性需求（QA scenario / SEI）

## 核心结论

1. **软件工程需求知识域已更新至 SWEBOK V4.0（2024-10 发布，18 个 KA）**，「软件需求」为 KA1，覆盖需求基础与分类、引出、分析、规格说明、验证、管理、实践考量与工具八簇，是需求领域的官方知识基线。软件需求定义沿用 V3：*a property that must be exhibited by something in order to solve some problem in the real world*（学界对此定义存有异议，属争议非错误）[S1-F01/S1-F08/S1-A01/S4-F02]。

2. **需求工程现行标准为 ISO/IEC/IEEE 29148:2018（第 2 版，2018-11，92 页）**，取代 29148:2011（IEEE 口径同时取代 IEEE 830/1233/1362）。截至 2026-09-10 状态为 Published (under review)，处于每 5 年定期系统评审（90.20，自 2023-10-15）；同时 P29148 为 Active PAR（修订草案进行中），尚无可替代版本 [S1-F02/S1-F03]。

3. **29148 过程链**：业务或任务分析 → 干系人需要与需求定义 → 系统[系统/软件]需求定义 → 需求管理；产出 BRS/StRS/SyRS/SRS。良构需求：单条须具备 necessary、appropriate、unambiguous、complete、singular、feasible、verifiable、correct、conforming 九特性；需求集须 complete、consistent、feasible、comprehensible、able to be validated；需求应述 what 而非 how [S1-F02/S4-F01/S3-F01]。

4. **干系人**定义为「对系统或其特性拥有权利、份额、主张或利益的个人或组织」，识别须覆盖多层级（用户、开发/维护/采购/操作/监管等）。干系人需要与干系人需求为两级对象：需求由需要转化而来、更结构化正式，需要记录冲突、一致性建立于系统需求层 [S1-F06/S1-F05/S4-F01]。

5. **质量属性需求以 QA scenario 六要素表达**：刺激源、刺激、环境、制品、响应、响应度量；功能与质量属性正交，是架构选择而非功能决定质量水平，故质量需求须在架构设计前显式、可度量。SEI 以 ATAM 做架构权衡评估 [S2-F01/S1-F07]。

6. **软件危机与本质复杂度**：Brooks《No Silver Bullet》（1986，本轮获取 UNC 原始 TR86-020）区分本质/偶然任务，提出本质困难四要素 complexity、conformity、changeability、invisibility，论证不存在银弹；2025 INCOSE NZ 对 5 个项目的合规审计显示需求质量薄弱点（假定未管理、优先级/难度未评估）今天仍具现实相关性 [S4-04/S1-07/S4-F01]。

- 29148:2018 系统评审结论与 P29148 修订发布计划未知。
- SWEBOK V4 正文未获取，KA1 目录取自官方 Topics 页 Wayback 快照（2024-12-12），小节定义依 V3 与目录标题推断；V3 镜像 PDF 损坏，定义原句经快照 + 学术转引交叉。
