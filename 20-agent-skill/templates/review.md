# 评审结论模板 · 架构评审与设计裁决

> 对应工程步骤「评审与设计裁决」（介入强度：产出级；主要场景 4、8）。
> 本模板为人类可读的评审结论结构，**无独立 schema、不单独过门控**；
> 其结论须人工确认后定稿，并回挂到对应 ADR / 边界说明。
> 质量属性场景**直接引用** ADR 的 `quality_scenarios`，不得在本模板内重复造一套。
> 所有节点 id 须先在 `<MISSION_ROOT>/10-dag-data/methodology-dag.json` 中核实存在，禁止编造。

## 一、章节说明

| 章节 | 必填 | 内容 | 支撑节点（示例） |
|---|---|---|---|
| 评审对象与范围 | 是 | 被评审的 ADR / 边界说明 / 设计文档及其版本、评审目的与不在范围内的事项 | — |
| 质量属性场景回顾 | 是 | 逐条引用被评 ADR 的 `quality_scenarios`（`stimulus` / `response` / `measure`），不重复造 | `MTH-G-02` |
| 敏感点 | 是 | 一动即影响多个质量属性的设计点，注明各属性受影响方向 | `MTH-G-06` |
| 权衡点 | 是 | 多个质量属性在此互相牵制、必须显式取舍之处 | `MTH-G-06`、`ESS-O-02` |
| 风险主题 | 是 | 潜在风险 + 影响 + 缓解措施（可含未决风险） | `MTH-G-01` |
| 非风险项 | 是 | 经审查确认无风险或可接受的项，避免评审只列问题 | — |
| 评审结论与建议 | 是 | 放行 / 有条件放行 / 打回，附条件与整改项 | `MTH-G-01` |
| 节点引用位 | 是 | `graph_refs`（ESS/MTH）+ `standards_refs`（TEC） | — |

> `graph_refs` 与 `standards_refs` 的分工同 ADR：
> 前者是"判据"（ESS/MTH），支撑评审判断；
> 后者是"标尺"（TEC），只用于外部对照，**绝不进入结论/建议等推荐位**。

## 二、措辞纪律（刚性）

- `TEC-` 节点 id **不得**出现在「评审结论与建议」「风险主题」等**推荐位**；
  `TEC-` 只允许写入文末 `standards_refs`。
- 引用技术实践层时统一用"以 `<TEC-节点名>` 作为选型标尺佐证"的措辞，
  **不得**写成"应选用 `<具体技术/厂商>`"。
- 结论须挂在可追溯的 ESS/MTH 判据上，而非个人偏好。

## 三、骨架（占位符）

```markdown

- 评审目的：<目的>
- 不在范围：<排除项>

## 2. 质量属性场景回顾
> 引用自 <ADR-xxx>.quality_scenarios，不重复造。
| # | stimulus | response | measure |
|---|---|---|---|
| 1 | <刺激> | <响应> | <可度量指标> |

## 3. 敏感点

## 4. 权衡点
- <设计点>：<属性A> 与 <属性B> 互相牵制，取舍依据（`<ESS/MTH-节点>`）

## 5. 风险主题
| 风险 | 影响 | 缓解 | 状态 |
|---|---|---|---|
| <风险> | <影响> | <缓解> | 已缓解/未决 |

## 6. 非风险项
- <经审查确认可接受或低风险的项>

## 7. 评审结论与建议
- 结论：<放行 / 有条件放行 / 打回>
- 条件 / 整改项：<...>
- 建议：<...>

## 8. 节点引用位
- graph_refs（ESS/MTH）：`<MTH-节点>`、`<ESS-节点>`
- standards_refs（TEC，仅选型标尺）：`<TEC-节点>`
```

## 四、填好的最小示例（场景 8 · 敏感点/权衡点评审）

以下节点 id 均已核实在 `methodology-dag.json` 中存在：
`MTH-G-02`、`MTH-G-06`、`MTH-G-01`、`ESS-O-02`、`MTH-M-06`、`TEC-G-01`。

```markdown
# 评审结论 · 内部工具平台运行时形态（ADR-001）

## 1. 评审对象与范围
- 评审对象：`ADR-001` 内部工具平台的运行时形态：模块化单体优先（proposed v1）
- 评审目的：裁决该决策是否可进入实现
- 不在范围：具体数据库与前端技术选型

## 2. 质量属性场景回顾
> 引用自 ADR-001.quality_scenarios，不重复造。
| # | stimulus | response | measure |
|---|---|---|---|
| 1 | 新增一类报表需求 | 在单个已定边界内完成开发与上线 | 变更触及模块数 <= 1，交付周期 <= 5 个工作日 |
| 2 | 发布新版本后发现回归缺陷 | 可整体回滚到上一版本 | 回滚时间 <= 10 分钟 |

## 3. 敏感点
- 模块边界划分：一动即同时影响可修改性与可演化性，边界过粗则变更扩散、过细则认知负荷上升（`MTH-G-06`）。

## 4. 权衡点
- 交付速度 vs 独立可扩展性：模块化单体提升前者、限制后者，须在接受退化后再定序（`ESS-O-02`、`MTH-M-06`）。

## 5. 风险主题
| 风险 | 影响 | 缓解 | 状态 |
|---|---|---|---|
| 模块边界纪律失守 | 耦合上升，未来拆分成本升高 | 引入适应度函数守护边界 | 未决 |
| 单点扩展受限 | 高负载场景需重构部署单元 | 预留已识别接缝，按需绞杀式拆分 | 已缓解 |

## 6. 非风险项
- 5 人团队下的运维负担：模块化单体显著低于服务拆分，判定可接受。

## 7. 评审结论与建议
- 结论：有条件放行
- 条件：实现阶段须产出并运行模块边界的适应度函数，边界变更需回挂本 ADR。
- 建议：以 MTH-G-06 的敏感点清单作为后续演进评审的检查项。

## 8. 节点引用位
- graph_refs（ESS/MTH）：`MTH-G-02`、`MTH-G-06`、`MTH-G-01`、`ESS-O-02`、`MTH-M-06`
- standards_refs（TEC，仅选型标尺）：`TEC-G-01`
```

> 说明：示例中 `TEC-G-01` 仅作为 `standards_refs` 的选型标尺佐证，
> 未出现在「评审结论与建议」「风险主题」等推荐位。
